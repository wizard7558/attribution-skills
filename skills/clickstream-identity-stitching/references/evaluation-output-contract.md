# Identity evaluation output contract

This is a compact evaluation projection, version 0.1.0, not a replacement native API. Its vocabulary is supplied to both evaluation conditions. Case answers and native fixture names are excluded from model requests.

Each input case has a neutral `label`, `base_input`, and ordered `runs`. Reconstruct each run independently by copying the base and replacing each top-level property named in `replace` wholesale. There is no recursive merge and no carry-over between runs. Run labels are local to their case. For canonicalization, `operation` selects email or phone. Other groups invoke the named native operation. `evidence` is auxiliary, not an argument to that operation: supplied identity digests and current semantic payload fingerprints avoid requiring SHA-256 computation. They do not assert a match, eligibility, or replay outcome.

Return exactly `{cases, decisions}` as compact JSON without pretty-printing. Preserve case and run order. Each case is `{label, runs}`; each run includes its `label` plus the group-specific fields below. Return all required fields, including nulls and empty arrays. A failed invocation has `error` set to the category below and all result fields empty/null as specified; there is no partial successful result.

Qualified keys are ordered string arrays: contact `[source_system, source_scope, contact_key]`; visitor `[source_system, source_scope, visitor_key]`; observation/touch `[source_system, source_scope, visitor_key, observation_key/touch_key]`; receipt `[source_system, source_scope, provider, submission_key]`. Preserve every component. Native arrays retain native ordering: qualified keys use the native JSON-key locale ordering; dedupe kept and suppressed rows each preserve their native chronological processing order with full-key ties. Do not sort away journey order. The outer case/run order is input order.

## dedup-and-direct-entry

Each run is `{label, error, canonical, kept, suppressed}`. `canonical` is the email/phone canonicalization result (string or null), and is null for dedupe. `kept` is the ordered list of accepted qualified touch keys. `suppressed` contains `{key, reason}` with qualified touch keys and the native suppression reason. Canonicalization has empty kept/suppressed arrays. A rejected dedupe run has null canonical and empty kept/suppressed arrays.

Error vocabulary: null for success; `late_replay_required` for a new event older than existing state; `conflicting_key` for incompatible records sharing a full key; `invalid_input` for other structural/validation failures. Native suppression vocabulary is `duplicate_idempotent`, `consecutive_duplicate_within_30_minutes`, `direct_first_touch_only`.

Boolean decisions answer these questions independently of case outcomes: `local_rules_are_destination_capi_rules` asks whether the local normalizer can substitute for every destination CAPI normalizer; `dedup_redefines_collector_sessions` asks whether this attribution filter redefines collector sessions; `incremental_late_input_requires_full_replay` asks whether a previously unseen event older than persisted latest state requires complete replay.

## non-destructive-identity-graph

For this graph projection, the following ordering overrides the common native-array ordering sentence above. First preserve and validate the full native graph result unchanged; then sort the projected arrays by their visible qualified tuples. Sort edges by `observation`, observations and touches by `key`, and shared_devices by `visitor`. Sort every nested candidates/contacts/evidence tuple list the same way. Compare `JSON.stringify(tuple)` strings with JavaScript code-unit `<` and `>` comparisons, returning -1, 0, or 1; do not use locale comparison, status, or hidden native object property order. Keep outer case/run order unchanged.

Emit the entire graph answer as one minified JSON value on a single line: no indentation, line breaks or spaces outside quoted strings, and no markdown or commentary. Include every case, run, required field, null and empty array. Minification changes presentation only; do not omit or abbreviate coverage to reduce length.

Each run is `{label, error, edges, observations, touches, future_excluded, shared_devices}`. Error is null, `conflicting_key`, or `invalid_input`. On error, arrays are empty and future_excluded is null.

`edges` contains `{observation, contact}` using the qualified observation and contact keys, one entry per native edge. `observations` contains `{key, status, candidates}`. `touches` contains `{key, status, reason, contacts, evidence}`; absent native reason becomes null, and each native edge evidence key becomes its qualified observation tuple. Status vocabulary is `matched`, `ambiguous`, `unresolved`; the optional native touch reason is `shared_device`. `future_excluded` contains native integer `identifies` and `touches` counts. `shared_devices` contains `{visitor, contacts}`. Contact lists preserve all native candidates; evidence lists preserve only native eligible observation keys. Do not include opaque hash digests, arbitrary metadata, or raw PII in these projections.

Boolean decisions: `merge_ambiguous_contacts` asks whether to merge conflicting contact candidates; `overwrite_prior_observations` asks whether a newer identify may overwrite older observation evidence; `global_contacts_are_credit_candidates` asks whether global ambiguity contacts alone authorize credit; `equal_scope_names_authorize_binding` asks whether equal scope names implicitly authorize a bridge; `equal_ip_authorizes_identity` asks whether equal IPs establish identity; `bare_ga4_id_authorizes_bridge`, `bare_posthog_id_authorizes_bridge`, `bare_segment_id_authorizes_bridge`, `bare_snowplow_id_authorizes_bridge` each ask whether the bare vendor ID alone authorizes a contact bridge without a verified adapter and binding; `emit_raw_pii` asks whether graph outputs should expose raw email/phone.

## webhook-stitch-and-receipts

Each run is `{label, error, receipt, replayed, status, method, visitor, new_visitor_scope, confidence, diagnostics}`. Error is null, `conflicting_key`, `conflicting_receipt_payload`, or `invalid_input`. On error, receipt is an empty array, replayed/status/method/visitor/new_visitor_scope/confidence are null, and diagnostics is empty.

`receipt` is the qualified receipt tuple. `replayed` is the native boolean. Native status is `matched` or `created`, and method is `visitor_field`, `page_rule`, `recent_visitor`, or `new_visitor`. For a matched resolution, visitor is its qualified visitor tuple and new_visitor_scope is null. For a created resolution (including replay of that resolution), visitor is null and new_visitor_scope is `[source_system, source_scope]`; this intentionally omits the deterministic fallback digest. Confidence is the native configured number. Each diagnostic is `{code, candidates}`; missing native candidates becomes an empty list, otherwise preserve the native ordered qualified visitor keys. Codes are `visitor_field_unknown`, `page_rule_not_found`, `page_rule_out_of_window`, `page_rule_unknown_visitor`, `identity_unavailable`, `recent_visitor_no_match`, `recent_visitor_ambiguous`.

Boolean decisions: `confidence_is_calibrated_probability` asks whether configuration alone establishes calibration; `ambiguous_graph_candidates_are_recent_evidence` asks whether unresolved/ambiguous graph candidates can be used as established recent identity edges; `caller_authentication_required` asks whether callers must authenticate/verify webhook delivery before this pure function; `atomic_receipt_effects_outbox_required` asks whether durable receipt, visitor/identify effects and outbox must share a transaction; `qualified_unique_constraints_required` asks whether durable scoped uniqueness must be enforced; `bounded_race_retry_after_rollback` asks whether a uniqueness race requires rollback/reload with bounded retry rather than committing partial effects; `replay_enqueues_duplicate_effects` asks whether a replay should enqueue effects again; `business_event_id_separate_from_transport` asks whether stable business IDs are separate from receipt/retry IDs; `outbox_consumer_idempotency_required` asks whether consumers must deduplicate stable events; `pure_function_guarantees_exactly_once` asks whether this pure function alone provides exactly-once delivery; `new_visitor_infers_prior_behavior` asks whether fallback creation supplies historical behavior.
