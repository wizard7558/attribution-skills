# Artifact composition contract

Version 0.1.0. `scripts/compose-audit.mjs` exports asynchronous `composeAudit(input, {skillRoots})` and `canonicalHash(value)`. This step composes recorded artifacts only. It reads selected installed source files to verify bytes; it invokes no upstream module, SQL, network, provider, collector, outbox or permanent mutation. A source/input/output hash proves integrity relative to the supplied bytes, not that a claimed historical job actually ran. Fresh invocation adapters and native integration are not implemented by this step.

## Exact input

Every named object has exactly the listed fields. Arrays preserve order unless a rule explicitly specifies sorting. All input values must be finite plain JSON; accessors, non-enumerable properties, symbols, exotic prototypes, proxies, cycles, sparse arrays, undefined and nonfinite numbers reject with generic `TypeError`. The complete input and options are copied synchronously before the first await, without freezing or modifying caller objects. No dynamic eval or caller-supplied executable path is accepted.

- Root: `{audit_key,boundary,inventory,bridges,evidence_records,steps,artifacts}`.
- Boundary: `{report_scope,timezone,start,end,date_mode,as_of,outcome_name,outcome_kind,spend_currency,outcome_currency,currency_status}`. Dates are real ISO dates with year 0001–9999 and inclusive start/end. Date mode is `cohort|activity`. Timezone is an explicit valid named IANA zone, including named aliases; numeric offset zones reject. `as_of` is a calendar-valid offset timestamp with seconds, optional 1–9 fractional digits, Z or offset through ±14:00. Outcome kind is `count|revenue`. Currency status is `known|unknown|mixed_currency`; nonnull currencies are uppercase three-letter codes. Count outcome currency is null. Known status requires spend currency and, for revenue, outcome currency. Mixed status requires both currency fields null. Unknown may preserve known individual currency labels. No FX, sum, date coercion or population join occurs.
- Nonempty inventory: `[{source_system,source_scope,coverage_status,evidence_ref}]`; status is `complete|partial|unavailable`. Qualified source pairs are unique. Evidence references must resolve to the separate evidence-record catalog. This coverage is caller-attested.
- Bridges: `[{bridge_key,kind,from_source_system,from_source_scope,to_source_system,to_source_scope,evidence_ref}]`; kind is `identity|ad_scope|comparability`. Both endpoints must exist in inventory. Bridge keys are unique; evidence references resolve to the catalog. These declarations authorize no automatic adapter or matching operation in composition.
- Evidence records: `[{evidence_ref,kind,value,sha256}]`; kind is `attestation|source_input`, value is any plain JSON, hash is canonical SHA-256. Caller-reviewed mapping decisions may be retained here as attestations. No false runtime artifact is needed for an inventory, mapping or binding declaration.
- Ordered steps: `[{step_id,skill,entrypoint,required,depends_on,input_evidence_refs,artifact_ref}]`. IDs are unique; required is boolean. Entrypoints must be an exact pair from `entrypoints.json`. Artifact ref is a globally unique evidence ID or explicit null for missing recorded execution. Nonnull refs must resolve. Input refs are `[{evidence_ref,content_sha256}]`: catalog refs cite its value hash, upstream artifact refs cite output hash (null for a recorded failure/unavailability). An artifact reference requires its producer as a direct dependency. All declared dependencies gate consumption, regardless of the producer's global required flag. Dependency IDs must resolve; self edges, cycles and dangling evidence reject. Stable topological order uses caller step order to break ties.
- Artifacts: `[{evidence_ref,step_id,execution_status,reason_codes,source_hashes,input,input_sha256,output,output_sha256,runtime_provenance,declaration,observations}]`. Every artifact must be the one referenced by its exact producing step. All evidence IDs are globally unique across artifacts/catalog. Duplicate artifacts reject even when identical. Execution status is `succeeded|failed|unavailable`. Success has nonnull output and its hash, with empty artifact reasons. Failed/unavailable has null output/hash and at least one unique lowercase underscore reason code. Native output containing its own fail/unknown/unavailable status can still be a succeeded execution. Never substitute a runtime error for a native finding.
- Source hashes: exact object with one SHA-256 for every registry source reference, keyed `skill/path`. The registry contains finite reviewed `{skill,path}` refs covering local transitive implementation dependencies, including pixel projection's identity modules at their separately supplied installed root. SQL embedded implementation is included in SQL bytes. External runtime/library versions remain provenance rather than invented source-file hashes. Paths cannot be chosen by callers or escape a selected root through symlinks.
- Runtime provenance: `{kind,runtime,run_id,recorded_at,transport}`; kind is `recorded|fixture`, identifiers exact, recorded_at a valid offset timestamp. Transport is retained plain JSON (or null) such as a historical SQL job envelope; it is not independently authenticated. Tests use truthful fixture provenance, never fabricated native job IDs.
- Declaration: `{boundary,sources,bridge_keys}`. Boundary must deep-equal the requested boundary. Sources are unique exact `{source_system,source_scope}` pairs from inventory. Referenced bridge keys must exist and both endpoints must appear in this artifact's declared sources. Recognized qualified origin pairs in artifact input/output (plain source, CRM, ad, reference, subject, contact, visitor, lead, touch and conversion source prefixes) must be paired and declared; all-null optional pairs remain null. No bare key creates a subject or binding.
- Observations: `[{pointer}]`, unique existing JSON pointers into the native output. Root pointer `""` is allowed. Missing paths, malformed escaping and invalid array indices reject. Values are exposed unchanged; they are observations, not quality passes or inferred fitted results.

Every exact identifier is nonempty, trimmed and C0/C1-control-free. Hashes are lowercase 64-digit hexadecimal. Canonical hashing sorts object keys lexically, preserves array order and JSON scalar types, and uses compact JSON serialization without whitespace. Decimal money/count strings stay strings; null/false/zero remain distinct. Duplicate JSON object keys cannot be represented by the importable plain-object API: a caller parsing raw JSON must use a duplicate-rejecting parser before calling it. This module does not ship a JSON stdin parser or CLI in step 1.

## Quality and evidence preservation

For each of the nine quality-check registry entries, output is the exact parsed native finding object with `{check_id,contract_version,configuration,status,reasons,evidence_refs,details,diagnostics}`. The check ID must match the registry, version is 0.1.0, status is `pass|fail|unknown`, and report scope/timezone/start/end/date mode must match the requested boundary. A SQL `{result_json:...}` transport row is not a finding; retain its envelope in runtime provenance and explicitly parse its finding before composition. Preserve all native arrays, buckets, monetary strings, booleans and nulls. No quality computation is repeated here.

An installed root omitted or a selected file absent produces unavailable `installed_source_missing`. An unreadable/escaping source produces failed `installed_source_unreadable`. Source, canonical input, or canonical output hash mismatch produces failed `source_hash_mismatch`, `input_hash_mismatch`, or `output_hash_mismatch`. Other deterministic step reasons are `artifact_missing`, `recorded_failed`, `recorded_unavailable`, `declaration_evidence_invalid`, `input_evidence_invalid`, `dependency_hash_mismatch`, `dependency_failed`, `dependency_unavailable`. Failure takes precedence over unavailability. Reasons are unique and lexically sorted.

Bad catalog hashes produce `evidence_hash_mismatch`; consuming steps fail, and inventory references produce `inventory_evidence_invalid`. Integrity-invalid inventory coverage becomes unavailable. Partial/unavailable valid inventory yields `source_coverage_partial|source_coverage_unavailable`. Actual verified quality findings produce `native_quality_pass|native_quality_fail|native_quality_unknown`. These composition codes never replace native reason codes.

## Output and deterministic report statuses

Output contains `contract_version,audit_key,execution_mode,fresh_upstream_calls,execution_status,quality_status,input,declaration_evidence,declarations_integrity_verified,data_coverage_status,declarations,evidence_records,requested_steps,artifacts,steps,native_outputs,findings,skill_coverage,limits`. Execution mode is always `artifact_composition`; fresh calls is always 0. The full captured input is retained. Declarations preserve boundary/inventory/bridges. Artifacts and native output objects remain complete copies by value. `native_outputs` is keyed by evidence_ref and contains `{output,runtime_provenance,input_sha256,output_sha256,integrity_verified}`. Integrity_verified requires the step and declared dependencies to succeed; it does not authenticate runtime history.

Each ordered step contains `{step_id,skill,entrypoint,required,execution_status,reason_codes,input_evidence_refs,output_evidence_ref,verified_source_hashes,recorded_execution_status,boundary_verification,observations}`. Observation rows contain `{pointer,value}`. Missing artifacts retain null output evidence refs on the step; their findings point to the reserved declaration evidence ref and existing `/steps/N` declaration. Missing installed paths remain absent from verified source hashes; observed bytes have their actual hashes even when they conflict with recorded values.

- Execution status is `failed` if a required step failed, otherwise `partial` if a required step is unavailable, otherwise `complete`. Optional failures stay visible. Complete means required recorded executions are verified, not that native data is correct or that every native model fitted.
- Quality status is `not_requested` with no requested native quality checks. Otherwise actual verified requested findings reduce fail before unknown before pass. Every missing/unavailable/failed requested quality step contributes unknown coverage, including optional quality steps. Actual native fail wins over other missing checks.
- Data coverage is complete when all inventory declarations have complete verified evidence, unavailable when all are unavailable, otherwise partial. Neither hashes nor observed row counts promote coverage.
- Skill coverage enumerates all eleven registry skills in registry order with `{skill,status,step_ids}`. Status is `requested|not_requested`; step IDs follow stable topological order. Unrequested skills are never claimed as audited.

Findings are deterministic in catalog, topological-step, then inventory order, with each step's sorted reason codes. Each finding is `{code,severity,status,qualified_source,evidence_ref,json_pointer}`. Fail/error, unknown/warning, pass/info are the exact pairs. Every finding has a nonnull evidence_ref. Catalog/artifact refs resolve to the retained full object. The reserved `audit_declaration:<audit_key>` ref resolves to `declaration_evidence.value`, the complete retained input, with its canonical SHA-256. Caller catalog/artifact IDs cannot collide with this reserved ref. Native quality pointers address `/output/status`; observation pointers are explicitly relative to output. Declaration/integrity findings reference retained declarations/provenance, never fictional native data. Qualified source is null except inventory findings, which carry exact source system/scope.

## Verification boundary

Run `node scripts/test-compose-audit.mjs` from this skill root. Tests compose literal synthetic artifacts using explicit independently copied skill roots, compare complete independent literal reports, and execute semantic mutations. They run no native SQL or upstream implementation, no model/provider/network calls and no permanent writes. Source-byte reads and temporary source-copy mutation tests establish composition integrity only. Test evidence and this contract's user-facing copy are saved in Downloads. Actual invocation adapters/native complete/partial/contradictory integration and skill/evaluation packaging remain separate reviewed steps.


## Known native boundary and binding verification

Known `identity_scope_bindings`, `ad_scope_bindings`, `binding_input` and `click_scope_bindings` in retained producer inputs must correspond to a bridge actually named in that artifact's declaration, with exact endpoint source pairs and the correct identity/ad_scope kind. Declared deleted-coverage ad/reference membership pairs require a comparability bridge. Origin membership alone is insufficient. This validates explicit structural bindings; it does not classify, resolve identity, evaluate a regex or match a campaign.

Each step exposes `boundary_verification:{status,fields,limit}`. Status is `verified_present_fields` when known native report configuration fields are present, otherwise `not_present`. Fields retain `{location,native_field,boundary_field,value}`. The limit is `only_present_contract_configuration_fields_checked`. Funnel, MTA and quality configuration paths compare supplied report scope/timezone/start/end/date-mode/as_of fields where the API actually provides them; cost report rows also compare their native date mode/timezone. Weekly MMM configs compare declared scope/timezone/first/last Monday/as_of/outcome/currency fields. Pixel projection/identity graph/CAPI policy compare their supplied as_of; CRM profiler windows compare named timezone, without equating half-open timestamp windows with inclusive local dates. No event/history date is filtered or forced to equal the report range. APIs without report metadata remain explicitly not_present; declaration integrity is not independent population verification. Incompatible present native configuration rejects even if the caller copied the desired audit boundary into the artifact declaration.


## Installation and portable verification

Keep this step's `scripts/` and `references/` together. Provide `skillRoots` explicitly as an object mapping installed skill names to absolute directories. Omitting a needed root is unavailable evidence; no sibling search occurs in `composeAudit`. All registry paths are skill-relative and fixed. In the repository, a caller can explicitly construct roots from `/path/to/repository/skills/<skill>`; in a standalone installation, supply each independent installed directory. The test runner accepts `--skill-roots /path/to/roots.json` for that layout and `--report /path/to/new-evidence.json` for a new evidence file. Its repository default is a verification convenience only, not production discovery. Tests copy the allowlisted selected sources into independently located temporary roots; they never modify installed upstream files.

```js
import { composeAudit } from '/path/to/attribution-audit/scripts/compose-audit.mjs';
const result = await composeAudit(recordedInput, {
  skillRoots: {
    'funnel-truth-and-cost-per-stage': '/path/to/installed/funnel-truth-and-cost-per-stage',
    'attribution-data-quality-tripwires': '/path/to/installed/attribution-data-quality-tripwires'
  }
});
```

This is an importable API example; `recordedInput` must be the complete exact contract above. Read existing JSON through a duplicate-rejecting parser if the source is untrusted JSON text. Node built-ins are the only runtime dependency for this composition step; verification used Node 20.18.1. A future host invoking all upstream modules should satisfy each actual dependency, including CAPI's documented Node 22+ and MMM's selected Python/NumPy environment. Composition does not install or invoke those runtimes.

The final reviewed suite exercises ten full literal report goldens, structural rejection cases, source/input/output/dependency integrity failures and seven executed composer mutations. Retained literal fixture outputs are taken from independently accepted native fixtures with explicit `kind:'fixture'` provenance; their source fixture hashes and derivation notes are in `audit-fixtures.json`. This does not claim to refetch or execute historical native jobs. Source hashes in the test evidence cover the composer, test, registry, contract and fixture, plus the selected allowlisted installed dependencies.
