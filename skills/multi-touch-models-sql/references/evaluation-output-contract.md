# Evaluation output projection

This public interface projects the native [ledger](ledger-contract.md) and [metrics](metrics-contract.md) outputs. It changes neither producer. Every outer input case has a neutral `case` label. Return exactly `{"cases":[{"case":label,"result":projection}]}` in input case order. Preserve every requested field, including nulls and empty arrays; add no other fields. Input arrays contain the complete supplied records, with omitted optional subject fields meaning null. If invocation metadata is omitted from raw ledger input, the outer case label supplies it; invocation labels do not influence credit. Native source keys and subject triples remain exact strings.

## Ledger projection

Both ledger groups return an object with `ledger`, `coverage`, and `diagnostics`.

Each `ledger` row contains exactly `source_system`, `source_scope`, `conversion_key`, `touch_source_system`, `touch_source_scope`, `touch_key`, `model`, `credit`. Each `coverage` row contains exactly `source_system`, `source_scope`, `conversion_key`, `model`, `eligible_touch_count`, `total_credit`, `status`. Diagnostics contains exactly `requested_lookback_days`, `effective_lookback_days`, `clamped`, `future_touches_excluded`, `future_conversions_excluded`, `outside_report_conversions`, `unresolved_touch_count`.

Credits and total credits are finite JSON numbers. Counts and lookback days are JSON integers. `clamped` is a JSON boolean. All remaining values are strings. No projected ledger field is nullable. The qualified conversion triple is the first three fields; the qualified touch triple is the next three. Count eligible qualified touches, including eligible touches receiving zero model credit. Preserve those zero-credit rows.

Use all five model names: `first_touch`, `last_touch`, `linear`, `position_based`, `time_decay`. First and last assign one to their respective chronological endpoint and zero to others. Linear assigns `1/n`. Position assigns one for one touch, halves for two, and `.4` to each endpoint plus `.2/(n-2)` to each middle touch for larger windows. Decay uses `2^(-relative_age_days/half_life_days)` normalized over eligible touches, measuring microseconds relative to the youngest eligible touch. Half-life is in days. These are descriptive attribution rules, not causal lift estimates.

Filter future touches and conversions at `as_of` but sequence all nonfuture conversion history before filtering conversions to inclusive local report dates. Clamp requested lookback to the configured minimum/maximum. Full lookback includes both timestamp endpoints. Segmented windows also require touch time strictly after the prior conversion, even if that conversion is outside the report. Acquisition credits only the first observed supplied conversion per subject; supplied history cannot establish lifetime completeness. Missing-subject conversions have separate qualified-conversion partitions and cannot match any real subject. Touches require the explicit subject triple; visitor keys, IP addresses, native users, and channel names do not bridge people.

Coverage statuses use this precedence: `unresolved_subject` for missing subjects; otherwise `acquisition_repeat_excluded` for acquisition repeats; otherwise `no_eligible_touches` when no touch is eligible; otherwise `credited`. Noncredited rows have count and total credit zero, with no invented ledger touch. Credited rows have the actual eligible qualified-touch count and total original model credit (one within `1e-12`).

Diagnostics count raw future touches/conversions excluded by `as_of` (including identical duplicate input rows); `outside_report_conversions` counts deduplicated nonfuture conversions outside the inclusive local date interval. `unresolved_touch_count` counts all deduplicated touches with missing subject triples, including future touches. `effective_lookback_days` is the clamped requested value, and `clamped` records whether it changed.

Ledger array order is ascending `(conversion_at, source_system, source_scope, conversion_key, model, touch_at, touch_source_system, touch_source_scope, touch_key)`. Coverage uses the same order through `model`. Timestamps used for ordering remain available in raw inputs even when omitted from the projection. Native default string ordering applies, including model-name lexical order. Do not regroup by channel or reorder ties by bare key.

## Monetary projection

The money group returns `allocation_ledger`, `channel_metrics`, and `uncredited_coverage`. It consumes the supplied actual ledger and coverage projections, selecting exactly `configuration.selected_model` and explicit qualified conversion membership. Spend has its independent qualified membership. These memberships allocate sources to one caller-owned population; they do not establish identity or prove pixels observe the same people.

Each allocation row contains exactly the eight ledger-projection fields above plus `allocated_value`, `allocated_currency`, `allocation_status`. Original `credit` remains a finite JSON number. Currency and amount may be null; status is one of `known`, `unknown`, `mixed_currency`, copied from original conversion money. Known amounts have known uppercase three-letter currency; unknown amount is null and may retain a declared currency; mixed amount and currency are null.

For known money, use BIGNUMERIC-cast original credits as monetary weights, normalize by their BIGNUMERIC total, and traverse touch time then full qualified touch key. Convert absolute NUMERIC value to integer `1e-9` units. Round cumulative normalized-weight endpoints to integer units (half away from zero); set the final endpoint to the exact absolute amount units. Allocate signed endpoint differences divided by `1e9`. This telescopes exactly to original conversion money. Small positive FLOAT64 credits can quantize to zero monetary weight while retaining their original attribution credit. Never multiply the repeated original conversion value into a group revenue sum. Unknown and mixed money yield null allocation on every touch. Zero-credit unknown rows remain visible without poisoning positive-credit known revenue.

Each channel metric contains exactly:

- `event_date`, `channel`, `credited_conversion_count`, `qualified_conversion_count`, `qualified_touch_count`, `zero_credit_row_count`, `row_kind`;
- `revenue_status`, `revenue_currency`, `allocated_revenue`, `revenue_reason`;
- `spend_fact_count`, `observed_spend_status`, `observed_spend_currency`, `observed_spend`, `spend_status`, `spend_currency`, `final_spend`, `spend_reason`;
- `cost_per_attributed_conversion`, `cost_reason`, `cac`, `cac_reason`, `roas`, `roas_reason`.

Dates and channels are strings. `credited_conversion_count` is the FLOAT64 sum of original selected credits, not a touch count. Qualified conversion and touch counts are distinct full qualified identities within the channel/date; zero-credit and spend-fact counts are integers. Revenue and spend aggregate independently before the full outer join on conversion date, channel, and taxonomy version. Currency does not partition the join. `row_kind` is `matched` when both aggregates exist, `credited_only` when only revenue rows exist (including zero-credit rows), or `spend_only` when only spend exists.

Revenue status is `mixed_currency` for any positive-credit mixed record or multiple positive-credit currencies; otherwise `unknown` if any positive-credit amount is unknown; otherwise `known`. A group with only zero-credit rows is known zero only when all observed conversion money is known in one currency, and otherwise unknown. Revenue currency is the uniquely consistent positive-credit currency unless explicit mixed, or the consistent known currency for a zero-credit-only group. Known revenue is the BIGNUMERIC sum of allocated values; unavailable revenue is null. A spend-only group has unknown revenue, null currency/amount, and `revenue_reason="no_attributed_revenue_currency"`. Otherwise revenue reason is null for known, `unknown` for unknown, or `mixed_currency` for mixed.

Observed spend status is `mixed_currency` for an explicit mixed record or multiple currencies, otherwise `unknown` when any fact amount is unknown, otherwise `known`; no matching fact yields `absent`. Observed currency is retained only if uniquely consistent and no explicit mixed fact; observed amount is the BIGNUMERIC sum only when known, otherwise null. Observed spend survives partial completeness. With `spend_complete=false`, final spend is null, status `unknown`, reason `incomplete_spend`. Otherwise matching facts supply their observed status/amount and null reason for known or their status literal as reason. Complete absence becomes known zero only if every declared spend source currency is known and identical, with `complete_absent_zero`; otherwise final amount is null, status `unknown` or `mixed_currency`, and reason `absent_unknown` or `absent_mixed_currency`. Final currency comes from observed facts if present, otherwise the unique nonnull declared currency if one exists; unknown status need not erase a uniquely declared currency.

Ratios use BIGNUMERIC safe division. Cost reason precedence is: unavailable spend's `spend_reason`; `negative_spend` for negative final spend; `no_attributed_conversions` for nonpositive attributed count; `numeric_failure` for unrepresentable division, a positive FLOAT64 denominator casting to zero, or nonzero numerator underflowing to zero; otherwise null. Cost is final spend divided by original attributed count only with null reason, preserving true zero spend as zero. CAC equals cost and shares its reason only for `new_customers` with acquisition mode and explicit complete-history attestation. Ordinary conversions yield null CAC and `not_new_customer_population`.

ROAS reason precedence is: unavailable revenue's `revenue_reason`; unavailable spend's `spend_reason`; `negative_spend`; `zero_spend`; `currency_mismatch` for null or unequal currencies; `numeric_failure` for unrepresentable division or nonzero numerator underflow; otherwise null. ROAS is allocated revenue divided by final spend only with null reason. Signed refunds can produce negative ROAS. Do not turn unknowns into zero or infer revenue currency from spend.

All money and ratios are exact nullable decimal JSON **strings**, never JSON numbers. Use native canonical fixed-point representation: no exponent, leading plus, unnecessary leading zeros, negative zero, decimal point for an integer, or trailing fractional zeros. Zero is `"0"`. Allocations use at most nine fractional digits; BIGNUMERIC sums and ratios use up to 38 fractional digits. Preserve exact decimal precision rather than rounding to cents or FLOAT64. Reason fields are nullable strings; successful ratios have null reasons.

Each uncredited row contains exactly `source_system`, `source_scope`, `conversion_key`, `model`, `status`. Preserve the original coverage status; no fake Direct row. Allocation order is ascending `(conversion_at, source_system, source_scope, conversion_key, touch_at, touch_source_system, touch_source_scope, touch_key)`. Channel metrics order is `(event_date, channel, taxonomy_version)`. Uncredited coverage order is `(conversion_at, source_system, source_scope, conversion_key)`. Ordering fields omitted from the projection are still read from inputs.

## Scoring boundary

Every projected scalar is checked. Original FLOAT64 credit and attributed-count fields use absolute tolerance `1e-12`; decimal strings, integer counts, booleans, nulls, labels and reason literals use exact typed equality. Every array has an independent exact cardinality check and indexed scalar checks, so numeric `1` and `1.0` are equivalent for credit but not for integer count fields. The schema specifies types and required structure only; expected values stay outside both model conditions. This projection evaluates bounded synthetic interpretation, not SQL execution, causal inference, production scale or population identity.
